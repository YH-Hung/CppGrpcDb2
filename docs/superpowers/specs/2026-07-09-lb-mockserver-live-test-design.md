# Live failover testing with MockServer via docker compose — design

Date: 2026-07-09
Status: approved

## Goal

Exercise the `greeter_failover_client` demo binary end-to-end against real
network endpoints: three gRPC mock servers in Docker plus an L7 proxy, driven
by a shell script that asserts on the client's stdout and exit codes. This
covers two paths the in-process tests (`tests/lb/test_failover_live.cpp`)
cannot:

1. Real containers stopped/started under the client (`docker compose stop`),
   not in-process server shutdown.
2. A single proxy-fronted endpoint where the app-level failover loop
   degenerates to one attempt and recovery falls back to gRPC's built-in
   service-config retry — the gap noted in `test_failover_live.cpp` (DNS
   multi-address round_robin needs infrastructure an in-process test lacks).

## Technology choices

- **MockServer 7.4.0** (`mockserver/mockserver:7.4.0`) as the gRPC mock
  backend. Since the 7.x monorepo rewrite it speaks native gRPC: proto
  descriptors via `MOCKSERVER_GRPC_DESCRIPTOR_DIRECTORY`, expectations
  preloaded from JSON via `MOCKSERVER_INITIALIZATION_JSON_PATH`, plaintext
  HTTP/2 accepted, gRPC and admin REST API share port 1080.
- **Envoy** (`envoyproxy/envoy:v1.31-latest`) as the L7 gRPC proxy for the
  built-in-LB fallback scenarios. Chosen over DNS round-robin because the
  client runs on the macOS host and cannot resolve Docker's embedded DNS;
  a proxy exposed on one host port gives the same "one endpoint, many
  backends" shape.
- **Shell script driver** testing the actual demo binary (approved over a
  gated GTest binary; no C++ test duplication, no docker control from C++).

## Layout

Self-contained under `tests/lb/mockserver/`:

```
tests/lb/mockserver/
  docker-compose.yml        # mock1, mock2, mock3, envoy
  generate_artifacts.sh     # writes gen/: descriptor + per-mock expectations
  envoy.yaml                # static cluster over the 3 mocks, round robin
  run_live_test.sh          # test driver (executable)
  gen/                      # generated at runtime — gitignored
    helloworld.dsc
    expectations/mock{1,2,3}.json
```

`.gitignore` gains `tests/lb/mockserver/gen/`.

## Components

### docker compose topology

Compose project name `lb-mockserver-live` (avoids collisions with the
devcontainer compose). Host port map:

| Host port | Service | Purpose |
|---|---|---|
| 50051–50053 | mock1–mock3 (port 1080) | direct gRPC endpoints + MockServer admin API |
| 50050 | envoy | proxy listener, HTTP/2 both sides |
| 127.0.0.1:9901 | envoy admin | readiness (`/ready`) only |

Each mock service mounts the shared descriptor dir read-only
(`MOCKSERVER_GRPC_DESCRIPTOR_DIRECTORY=/descriptors` ← `./gen`) and its own
expectation file (`MOCKSERVER_INITIALIZATION_JSON_PATH` ← one file from
`./expectations`).

### MockServer expectations

One file per instance, generated by `generate_artifacts.sh` into
`gen/expectations/`; matches `POST /helloworld.Greeter/SayHello` with no body
matcher (any request name, including the client's non-ASCII default) and
replies with a distinct message naming the instance and host port.

**Amended after live validation (2026-07-10).** The documented JSON-body
format does not work: MockServer 7.4.0 (and the current snapshot) decodes
gRPC requests via the descriptor but never re-encodes a JSON response body to
protobuf, and it only emits gRPC trailers when the expectation defines them
explicitly — a JSON body reaches gRPC clients as raw text (`Bad GRPC frame
type 0x7b`, confirmed with both grpc-c++ and grpcurl, h2c and TLS). The
working format pre-encodes the reply as gRPC wire bytes (5-byte frame header
+ serialized `helloworld.HelloReply`):

```json
[
  {
    "httpRequest": {
      "method": "POST",
      "path": "/helloworld.Greeter/SayHello"
    },
    "httpResponse": {
      "statusCode": 200,
      "headers": { "content-type": ["application/grpc"] },
      "body": { "type": "BINARY", "base64Bytes": "<framed HelloReply>" },
      "trailers": { "grpc-status": ["0"] }
    }
  }
]
```

Because the payload must be computed with `protoc`, expectations are
generated at runtime alongside the descriptor (message text lives in
`generate_artifacts.sh`, the single source of truth) rather than checked in
as static files.

### Envoy config (`envoy.yaml`)

- Listener `0.0.0.0:50050`, HTTP connection manager, HTTP/2.
- Static cluster `greeter_mocks`: endpoints `mock1:1080`, `mock2:1080`,
  `mock3:1080` (compose service DNS), `lb_policy: ROUND_ROBIN`, upstream
  explicit HTTP/2 (h2c).
- **No active health checks and no Envoy-side retries** — a stopped backend
  keeps getting picked and fails the call, which is exactly what must surface
  to the client so its channel-level retry policy does the recovery.
- Admin on 9901 for readiness.

### Runtime artifact generation

`generate_artifacts.sh` produces everything under `gen/` before `compose up`
(never checked in, matching the repo rule that generated proto artifacts stay
out of git): the descriptor set via `protoc --descriptor_set_out
--include_imports`, and the three expectation files with `protoc
--encode=helloworld.HelloReply` + a python3 one-liner adding the 5-byte gRPC
frame header and base64. `run_live_test.sh` invokes it; manual `docker
compose up` users must run it first (the mock mounts point into `gen/`).

### Client extension: `greeter_failover_client [count] [delay_ms]`

`src/greeter_failover_client.cpp` currently makes exactly one call per
process, and the round-robin cursor is in-process state starting at endpoint
0 — so repeated runs always hit endpoint 0 and neither rotation nor cooldown
rejoin is observable across runs. Extension:

- `argv[1]` = number of sequential calls, default 1; `argv[2]` = delay
  between calls in ms, default 0. No flags parsing — positional, both
  optional. Invalid/non-numeric args → usage message, exit 2.
- One `FailoverClient` constructed once; per call print the existing line
  format unchanged (`Greeter received: <msg> (via <target>)` on success,
  `<code>: <message>` on failure) — the script asserts on these exact shapes.
- Exit 0 iff every call succeeded, else 1.
- Default invocation (`./greeter_failover_client`) behaves exactly as today.

## Test script: `run_live_test.sh`

CLI: `run_live_test.sh [--keep] [--client PATH]`.
Defaults: client `./build/greeter_failover_client`, repo root derived from
the script's own location. `--keep` skips teardown so the stack stays up for
manual poking.

Prerequisite checks (fail fast, clear message): `docker compose` available,
`protoc` on PATH, client binary exists (hint: `cmake --build build`).

Startup: generate descriptor → `docker compose up -d` → poll readiness:
mocks via `curl -s -X PUT http://127.0.0.1:5005X/mockserver/status`, envoy
via `curl -s http://127.0.0.1:9901/ready`, bounded (~30 s) with clear timeout
failure. Teardown: `trap` runs `docker compose down` on any exit unless
`--keep`.

Client env per scenario:
- Direct scenarios: `GRPC_TARGET_ENDPOINTS=127.0.0.1:50051,127.0.0.1:50052,127.0.0.1:50053`
- Proxy scenarios: `GRPC_TARGET_ENDPOINTS=127.0.0.1:50050`

### Scenarios (execution order)

1. **Direct round-robin** — all mocks up; one run `count=6` → exit 0 and the
   6 `via` targets are the strict rotation 50051, 50052, 50053, 50051, 50052,
   50053; each reply message names the matching mock.
2. **Failover skips stopped container** — `docker compose stop mock1`; run
   `count=4` → exit 0, no line says `via 127.0.0.1:50051`, all messages from
   mock2/mock3.
3. **Cooldown rejoin** — with mock1 still stopped, launch a background run
   `count=30 delay_ms=500` (~15 s window); immediately `docker compose start
   mock1` and wait for its readiness in the foreground; assert the run exits
   0 and `via 127.0.0.1:50051` appears somewhere in the output. Since mock1
   was down when the run started, any occurrence proves rejoin. The window is
   generous on purpose: MockServer's JVM takes seconds to boot, and each
   failed re-probe of mock1 grows its cooldown (exponential backoff, capped),
   so the rejoin point can land several seconds in.
4. **Proxy round-robin (built-in LB behind one endpoint)** — all mocks up;
   run `count=6` against the proxy → exit 0, every line says
   `via 127.0.0.1:50050` (served_by constant — app-level LB sees one
   endpoint), and the reply messages include all three mock identities —
   distribution happened behind the proxy.
5. **Built-in retry recovers a dead backend through the proxy** —
   `docker compose stop mock2`; run `count=6` via proxy → exit 0 (Envoy picks
   the dead backend for some calls → UNAVAILABLE → the channel's
   service-config retryPolicy (maxAttempts=4, retriable on UNAVAILABLE,
   active because single endpoint → `multi_endpoint=false`) re-attempts →
   lands on a live backend), exactly 6 lines all `via 127.0.0.1:50050`,
   messages only from mock1/mock3. Recovery alone could also mean Envoy
   quietly dropped the dead endpoint, so the scenario additionally asserts
   Envoy's `cluster.greeter_mocks.upstream_cx_connect_fail` counter grew
   across the run — proof the stopped backend was actually picked and the
   failures were absorbed by the client's retry. This is in-process live
   test #11's scenario through real network infrastructure.
6. **All endpoints down** — `docker compose stop mock1 mock3` (mock2 already
   stopped); run `count=1` against the three direct endpoints → exit 1 and
   stdout contains status code 14 (UNAVAILABLE). Runs last so no restart
   choreography is needed.

Output: per-scenario PASS/FAIL lines plus a final summary; non-zero exit if
any scenario failed.

## Error handling

- Docker daemon not running / image pull failure → prerequisite or compose
  step fails with the underlying error shown; teardown trap still runs.
- Readiness timeout → fail the run, print `docker compose logs --tail` for
  the unready service.
- Scenario assertions print the full client output on failure.

## Out of scope

- CI integration (script is for local runs; wiring into CI is a separate
  decision).
- TLS endpoints, streaming RPC scenarios, DB2-backed servers.
- Mutating MockServer expectations mid-run via its REST API (all behavior is
  driven by container stop/start).
